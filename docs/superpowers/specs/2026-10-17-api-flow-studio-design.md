# طراحی API Flow Studio

تاریخ: ۲۰۲۶-۱۰-۱۷

## هدف و معیار موفقیت

یک وب‌اپ محلی و مستقل برای ساخت و اجرای فلوهای HTTP از روی Swagger/OpenAPI هر پروژه ساخته می‌شود. کاربر می‌تواند چند پروژه با schema و base URL مستقل داشته باشد، فایل YAML یا JSON هر پروژه را وارد کند، endpointها را به ترتیب بچیند، مقدارهای ورودی را ثابت یا متغیر کند، فیلدهای پاسخ را در متغیرها ذخیره کند، هنگام ورودی دستی مثل OTP مکث کند و از هر مرحله با مقدارهای قبلی ادامه دهد. نمای اجرا تمام درخواست‌ها و پاسخ‌ها را به ترتیب، با URL، متد، JSON، کد HTTP و زمان نشان می‌دهد.

برنامه در پوشهٔ مستقل `api-flow-studio/` قرار می‌گیرد و هیچ وابستگی اجرایی به کد CLM ندارد. رابط فارسی و راست‌به‌چپ است. CLM تنها یک قالب آمادهٔ قابل ویرایش است که از ورود تا وضعیت `signing` قرارداد v2 را پوشش می‌دهد؛ امضای واقعی قرارداد در دامنهٔ این قالب نیست.

## شکل برنامه

- یک سرور محلی Python روی `127.0.0.1` رابط وب، API داخلی و اجرای درخواست‌ها را ارائه می‌کند. پورت پیش‌فرض ابزار `8765` است و هر پروژه base URL مقصد جداگانه دارد؛ برای نمونهٔ CLM محیط فعلی `http://127.0.0.1:8000`.
- SQLite پروژه‌ها، نسخه‌های schema، endpointهای شناخته‌شده، فلوها، متغیرها، اجرای گام‌ها و تاریخچه را نگه می‌دارد. فایل داده خارج از Git است و فقط کاربر سیستم‌عامل به آن دسترسی دارد.
- رابط وب بخش‌های «Swagger»، «Endpointها»، «فلو»، «متغیرها» و «تاریخچهٔ اجرا» دارد. فلو یک فهرست مرتب و قابل جابه‌جایی است. ویرایشگر هر گام URL، path/query/header، بدنه و نگاشت‌های خروجی را نشان می‌دهد. بدنه‌های JSON و `multipart/form-data`، از جمله فایل انتخاب‌شده در مرورگر، قابل تنظیم‌اند.
- API مقصد از سرور محلی فراخوانی می‌شود تا اجرای فلو وابسته به CORS مرورگر نباشد. ارتباط ابزار فقط روی loopback گوش می‌دهد.

## ورود و به‌روزرسانی OpenAPI

کاربر می‌تواند فایل YAML/JSON را بارگذاری کند، متن آن را بچسباند، یا URL schema را وارد کند. parser امن YAML استفاده می‌شود و ورودی Swagger 2.0 یا OpenAPI 3.x از نظر ساختار `paths` و اندازهٔ فایل بررسی می‌شود. فهرست عملیات در محدودهٔ همان پروژه با کلید پایدار `method + path template` نگهداری می‌شود؛ `operationId` و توضیحات، دادهٔ نمایشی و کمکی‌اند.

در import مجدد، عملیات هم‌کلید با تعریف تازه به‌روز می‌شوند و عملیات تازه اضافه می‌شوند. عملیاتی که دیگر در schema نیست، حذف نمی‌شود و با برچسب «در schema جدید نیست» باقی می‌ماند. فلو، مقدار متغیرها، template درخواست، نگاشت خروجی، checkpoint و تاریخچه دست‌نخورده می‌مانند. برنامه تغییرات مهم ورودی/خروجی هر عملیات را در یک گزارش diff نشان می‌دهد؛ گامی که مرجعش دیگر معتبر نیست برای بازبینی علامت می‌خورد و بدون تأیید کاربر به endpoint دیگری وصل نمی‌شود.

Schema زندهٔ CLM در `http://127.0.0.1:8000/api/schema/?format=json` در زمان طراحی با HTTP 200 و ۲۳۵ مسیر در دسترس بود. فایل OpenAPI فعلی frontend قدیمی‌تر است و مسیر `send-for-signing` را ندارد؛ بنابراین نمونه‌فلو با schema زندهٔ backend ساخته و اعتبارسنجی می‌شود. وارد کردن فایل YAML جدید بعداً همین داده را به‌روزرسانی می‌کند.

## متغیرها و قالب درخواست

هر پروژه متغیرهای نام‌دار با مقدار JSON، نوع نمایشی و نشان «حساس» دارد. کاربر می‌تواند مقدار را دستی وارد یا ویرایش کند؛ نگاشت خروجی نیز می‌تواند کل پاسخ یا یک مسیر از پاسخ را در همان متغیر بنویسد. مسیرهای پاسخ، کلید تودرتو و اندیس آرایه را پشتیبانی می‌کنند، مانند `tokens.access` و `[0].id`. نام و مقدار متغیرها بین پروژه‌ها جداست.

در path، query، header و بدنهٔ JSON یا فرم می‌توان به متغیر ارجاع داد. ارجاعی که تمام مقدار یک فیلد را تشکیل دهد، نوع JSON را حفظ می‌کند؛ جای‌گذاری در متن، رشته تولید می‌کند. پیش‌نمایش درخواست، مقدار نهایی URL و بدنه را پیش از اجرا نشان می‌دهد. متغیر ناموجود یا مسیر پاسخ نامعتبر باعث توقف گام با خطای قابل فهم می‌شود؛ مقدار قدیمی متغیر به‌صورت خاموش بازنویسی نمی‌شود.

یک گام دستی نیز می‌تواند متغیرهایی مثل `otp` را درخواست کند. این گام شبکه‌ای اجرا نمی‌کند؛ فلو روی آن مکث می‌کند و پس از ثبت مقدار به گام بعدی می‌رود. مقدارهای `mobile`، `national_id`، `address`، `otp`، توکن، tenant UUID و contract UUID همگی با همین سازوکار قابل استفاده‌اند.

## اجرای فلو و ادامه از هر نقطه

اجرا ترتیبی است. هر گام قبل از ارسال، همهٔ ارجاع‌ها را حل می‌کند و پس از دریافت پاسخ، نتیجه و checkpoint را ثبت می‌کند. فقط پاسخ موفق و نگاشت‌های معتبر، متغیرها را به‌صورت یک‌جا به‌روز می‌کنند. خطای HTTP، timeout یا شکست نگاشت، ادامهٔ خودکار را متوقف می‌کند و مقدارهای قبلی و تاریخچه را حفظ می‌کند. کاربر می‌تواند درخواست را اصلاح کند، همان گام را دوباره اجرا کند، یا از هر گام انتخابی اجرای تازه‌ای را با متغیرهای ماندگار شروع کند.

«ادامه» گام‌های موفق قبلی را تکرار نمی‌کند. «اجرای دوباره» همان گام را واقعاً دوباره فراخوانی می‌کند؛ برای متدهایی مانند POST که ممکن است منبع تکراری بسازند، رابط پیش از اجرا هشدار می‌دهد. هر اجرا شناسه و تاریخچهٔ مستقل دارد، ولی متغیرهای پروژه بین اجراها باقی می‌مانند. پاسخ‌های جدید متغیرهای نگاشت‌شده را به‌روز می‌کنند؛ بقیهٔ متغیرها حفظ می‌شوند.

احراز هویت در هستهٔ برنامه یک header template معمولی است؛ نام متغیر توکن و شکل header برای هر فلو قابل تنظیم است. نوسازی خودکار توکن نیز اختیاری و بر اساس endpoint، بدنه و نگاشت خروجیِ تعریف‌شده در همان پروژه است، نه یک مسیر ثابت در کد. اگر درخواست احرازشده ۴۰۱ بگیرد، runner یک بار گام refresh تنظیم‌شده را اجرا و درخواست اصلی را تکرار می‌کند. اگر refresh رد شود، فلو مکث می‌کند تا کاربر مراحل ورود را دوباره اجرا کند؛ سایر متغیرها حفظ می‌شوند. درخواست refresh و تلاش دوباره نیز در تاریخچه دیده می‌شوند. قالب CLM این تنظیم را برای `POST /api/auth/token/refresh/` و متغیرهای access/refresh از پیش پر می‌کند.

## نمای درخواست و پاسخ

تاریخچه به ترتیب واقعی رخدادها نمایش داده می‌شود؛ برای هر تلاش URL کامل، متد، query، headerهای قابل نمایش، JSON درخواست، کد HTTP، JSON پاسخ، مدت، خطا و نام گام ثبت می‌شود. در درخواست multipart، نام فایل و فیلدهای فرم جای بایت‌های فایل نمایش داده می‌شوند. برای پاسخ غیر JSON، نوع محتوا، اندازه و متن امنِ قابل نمایش نشان داده می‌شود. مقدارهای حساس مانند OTP، کد ملی و توکن در نمای پیش‌فرض پوشیده‌اند و کاربر می‌تواند در نشست محلی آن‌ها را آشکار کند. دادهٔ کامل برای ادامهٔ فلو در SQLite محلی ذخیره می‌شود؛ برنامه آن را در لاگ کنسول چاپ نمی‌کند.

## قالب آمادهٔ CLM: «ایجاد قرارداد v2 تا ارسال برای امضا»

متغیرهای دستی آغازین: `mobile`، `national_id`، `contract_title`، `contract_end_date`، `contract_content` و `signer_user_id`. `contract_content` بدنهٔ `content` در درخواست ساخت است و `json` سند TipTap و `html` متن رندرشدهٔ همان سند را دارد؛ یک مقدار پیش‌فرض ساده و معتبر برای آن ارائه می‌شود. `signer_user_id` باید به یک حساب موجود و متفاوت از حساب تأییدکننده اشاره کند؛ backend اجازه نمی‌دهد یک شخص دو نقش در یک قرارداد داشته باشد. `tenant_id` به‌طور پیش‌فرض از اولین عضو پاسخ tenantها گرفته می‌شود، ولی کاربر می‌تواند پیش از ساخت قرارداد آن را تغییر دهد.

| گام | درخواست/کار | نتیجه یا شرط |
| --- | --- | --- |
| ۱ | `POST /api/auth/send-otp/` با `mobile` و `national_id` | ارسال پیامک |
| ۲ | گام دستی `otp` | مکث تا ورود کد |
| ۳ | `POST /api/auth/verify-otp/` با `mobile`، `national_id` و `otp` | ذخیرهٔ `tokens.access`، `tokens.refresh` و `user.id` |
| ۴ | `GET /api/tenants/` | ذخیرهٔ `[0].id` در `tenant_id` |
| ۵ | `GET /api/v2/tenants/{tenant_id}/contracts/` | نمایش فهرست با همان tenant UUID |
| ۶ | `POST /api/v2/tenants/{tenant_id}/contracts/` با عنوان و محتوای قرارداد | ذخیرهٔ `id` در `contract_id` و پاسخ ساخت |
| ۷ | `PATCH /api/v2/tenants/{tenant_id}/contracts/{contract_id}/` | ثبت `end_date` و تغییرهای لازم پیش از انتشار |
| ۸ | `POST /api/v2/tenants/{tenant_id}/contracts/{contract_id}/parties/` | افزودن طرف با عضو `signer` از `signer_user_id` و عضو `approver` از `user.id` |
| ۹ | `POST /api/v2/tenants/{tenant_id}/contracts/{contract_id}/publish-for-review/` | وضعیت `under_approval` |
| ۱۰ | `POST /api/v2/tenants/{tenant_id}/contracts/{contract_id}/verdict/` با `state=approved` | ثبت رأی حساب واردشده |
| ۱۱ | `GET /api/v2/tenants/{tenant_id}/contracts/{contract_id}/` | بررسی `contract.status=approved` |
| ۱۲ | `POST /api/v2/tenants/{tenant_id}/contracts/{contract_id}/send-for-signing/` | بررسی `contract.status=signing` |

فلو پس از گام ۶ checkpoint دارد؛ در اجرای بعدی می‌توان از گام ۷ با `contract_id` ذخیره‌شده ادامه داد. اگر backend برای ارسال، پیوست یا استعلام اجباریِ یک قالب را لازم بداند، پاسخ ۴۲۲ در تاریخچه می‌آید و کاربر می‌تواند گام‌های لازم را پیش از گام ۱۲ به فلو اضافه کند. نمونهٔ پیش‌فرض قرارداد تازه و بدون قالب می‌سازد تا این وابستگی‌ها را تحمیل نکند.

## آزمون و معیار پذیرش

آزمون‌های خودکار با یک سرور HTTP ساختگی، این حالت‌ها را بررسی می‌کنند: دو پروژهٔ مستقل؛ import Swagger 2.0 و OpenAPI 3.x؛ import مجدد بدون از دست رفتن فلو و متغیرها؛ تزریق مقدار در path/query/header/body؛ درخواست multipart؛ استخراج فیلد تودرتو و اندیس آرایه؛ مکث ورودی دستی؛ ادامه از گام دلخواه پس از راه‌اندازی دوباره؛ توقف در خطا؛ هشدار اجرای دوبارهٔ POST؛ refresh قابل تنظیم؛ و ترتیب و محتوای تاریخچه. آزمون UI نیز ساخت و ویرایش فلو و نمایش JSON درخواست/پاسخ را پوشش می‌دهد.

آزمون نهایی با schema زندهٔ backend روی `127.0.0.1:8000` انجام می‌شود: اعتبارسنجی وجود همهٔ operationهای فلو، اجرای گام‌های بدون تغییر داده، و در صورت فراهم بودن شماره/کد ملی و OTP آزمایشی و `signer_user_id` معتبر، اجرای واقعی تا `contract.status=signing`. اجرای واقعی گام آخر پیام یا اعلان امضا ایجاد می‌کند؛ این اثر در صفحهٔ اجرا پیش از شروع فلو نمایش داده می‌شود. نبود دادهٔ آزمایشی یا سرویس‌های وابسته، به‌عنوان محدودیت تست زنده گزارش می‌شود و نتیجهٔ آزمون ساختگی جای آن معرفی نمی‌شود.

## خارج از دامنهٔ نسخهٔ نخست

اجرای موازی یا شرطی گام‌ها، چندکاربره‌بودن ابزار، زمان‌بندی خودکار، و انجام خودِ امضا در این نسخه نیست. فایل‌های بزرگ و پاسخ‌های باینری در تاریخچه به‌صورت متادیتا نمایش داده می‌شوند؛ بایت کامل آن‌ها در SQLite ذخیره نمی‌شود.
